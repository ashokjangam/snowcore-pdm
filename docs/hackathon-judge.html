Hackathon judge: what to pursue next

Two independent LLM judges assessed one submission each against the written Predictive Maintenance and OEE Command Center brief. Neither judge saw the other product. Both declined to advance its submission.

SNOWCORE
Do not advance as-is
Strong Snowflake shape; the trained model does not drive the operator workflow and all business data is generated.
PNEUMORA
Do not advance as-is
Stronger evidence and observed OT data; it detects most leaks after onset and its ERP/OEE context is synthetic.
Recommended direction
Hybrid
SNOWCORE platform + PNEUMORA evidence discipline + a dataset that supports genuine before-onset prediction.
Do not choose by total score. The totals are 35 for SNOWCORE and 36 for PNEUMORA after the Snowflake bonus. A one-point difference between two one-pass judges is noise, not a winner.
Decision. If the deadline is immediate, pursue SNOWCORE as the submission shell because it already has the native Snowflake architecture, semantic layer and command-center breadth. Replace its prediction and action path with tested evidence, not generated claims. Preserve PNEUMORA as the reference implementation for data provenance, leakage-safe evaluation, controls and honest promotion gates.

What each solution actually does

SNOWCORE

  • Trains a real SNOWFLAKE.ML.CLASSIFICATION model on a synthetic 1–7 day failure label.
  • Claims chronological holdout AUC 0.766 and, at threshold 0.05, recall 88.3% with precision 26.4%.
  • The command center never calls that model. Its shown risk is a current-health formula.
  • Telemetry, work orders, ERP-like dimensions, production and OEE are generated by SQL.
  • “Create work order” displays a toast and does not persist an order.

PNEUMORA

  • Uses observed public MetroPT compressor telemetry and published failure windows.
  • No predictive model is promoted: NO_PROMOTION.
  • External detector catches 2 of 3 air leaks, 72 and 86 minutes after onset, with one false alert over 167 healthy days.
  • The existing alarm catches the same two external leaks 15–20 minutes earlier, but with 57 false alerts.
  • Maintenance, production and OEE context are clearly labelled synthetic.

Enhancement plan

NOW Serve one real prediction path end to end

Write model scores to a versioned Snowflake table with model_version, scored_at, horizon, threshold, confidence and top contributing features. Make every command-center risk card read that table. Remove the separate health-score probability.

Acceptance: one asset and timestamp can be traced from raw signals → features → model score → alert → operator action.

NOW Make action real

Replace the toast with a Snowflake stored procedure or transactional write to WORK_ORDERS. Enforce idempotency so one alert cannot open duplicate orders. Record acknowledgement, assignee, parts, status, completion, disposition and whether the alert was useful.

Acceptance: pressing Create changes a table and the change survives reload.

NOW Separate forecast, detection and safety alarm

Show three distinct lanes: predicted failure before onset, developing-fault detection after onset, and reactive safety alarm. Score all timings against failure start and also report time remaining before operational removal. Never combine those metrics.

Acceptance: every alert says “forecast,” “detection,” or “reactive,” with signed minutes versus onset.

NEXT Put training, scoring and monitoring in Snowflake

Land observed telemetry in dynamic tables or incremental transforms; build point-in-time-correct features; train Snowflake ML on a chronological split; schedule scoring with Streams and Tasks; store performance and drift metrics. Keep a frozen holdout that is never used for threshold selection.

Acceptance: a task retrains only when approved, another scores new rows, and a registry table ties every score to its training data and metric artifact.

NEXT Add evidence-backed natural-language RCA

Give Cortex a semantic view over score explanations, recent sensor deviations, maintenance history, similar past failures, parts and manuals. Require answers to cite rows/documents and distinguish observed evidence from hypotheses.

Acceptance: test 15 fixed questions; score factuality, citation validity and abstention when evidence is missing.

DATA Replace assumed business context

Ingest a real CMMS/ERP extract: asset, order, failure mode, opened/completed timestamps, labour and parts. Add production counts, ideal cycle time, planned time, downtime and rejects. If real data is unavailable, state “scenario” everywhere and do not call the result measured savings or OEE lift.

Acceptance: every business metric has a source identifier and lineage to a non-generated record.

MEASURE Prove OEE lift, not an OEE chart

Compute Availability × Performance × Quality from production records. Compare treated alerts with a predeclared baseline using matched assets/time windows. Report avoided downtime and confidence intervals; do not annualise a synthetic holdout as realised savings.

Acceptance: show baseline OEE, post-action OEE, sample size, method and uncertainty.

Snowflake-native architecture worth building

Ingest and govern

Snowpipe Streaming or staged loads → raw immutable tables → dynamic tables for aligned OT/IT events. Add tags, row access, quality checks and lineage.

Predict and monitor

Snowflake ML training and model registry → scheduled scores → alert table → metric and drift tables. The UI reads persisted model outputs, never a second formula.

Explain and act

Cortex Analyst/Search over governed evidence → cited RCA → procedure-backed work-order creation → outcome feedback for evaluation.

Training the existing PNEUMORA rule in Snowflake alone is not enough. The limiting factor is target/data suitability, not where the same model runs.

What the short plan will not achieve

  • Wiring SNOWCORE's current model into the UI improves completeness but does not make synthetic evidence real.
  • Moving PNEUMORA training into Snowflake improves native-feature credit but does not turn post-onset detection into a forecast.
  • Adding an LLM explanation does not prove root cause unless it cites maintenance and sensor evidence.
  • Displaying work orders is not automation unless the action is persisted, governed and auditable.
  • Showing OEE is not lifting OEE. A lift claim needs production records and an evaluation design.
Genuinely unknowable without new data: whether either approach will predict real plant failures early enough, its production false-alert rate, causal OEE lift and realised savings. No amount of UI work can answer those questions.

Brief, honest pitch after enhancement

Suggested pitch. “We built a Snowflake-native command center that aligns OT telemetry with maintenance and production events, scores a versioned failure model, explains each alert from governed evidence, and creates an auditable work order. We distinguish forecasts from developing-fault detection and safety alarms. On the frozen chronological holdout, the model achieved [measured values]; on production data, OEE impact is [measured / not yet measured].”

Replace bracketed text only with stored, reproducible results. If the business data remains synthetic, say “demonstration scenario” in the pitch.
